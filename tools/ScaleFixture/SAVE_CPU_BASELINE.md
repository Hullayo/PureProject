# 20,000 任务保存 CPU 历史基线

本文记录 2026-10-06 修复前实现的历史测量，不是 2.0.1 当前实现的性能结论。后续生产代码已采用项目级快照、限制历史保留，并改造后台保存与 `SaveTask` 克隆范围；本文数值和实现描述保留用于对比。`SerializationBenchmark.cs` 仍按旧链路的步骤调用当前 Core 方法，重新运行会得到混合基准，不能声称复现原二进制或测得当前端到端保存性能。当前验收状态见 [修复与发布验证](../../docs/STRESS_REMEDIATION_20261006.md)。

2026-10-06 在原测试机器上运行 Release 只读基准，当时 `CommitAsync` 在开始文件 I/O 前的数据步骤中位数为 **758.9 ms**，范围 **691.9–1,075.9 ms**，每轮分配 **604.4 MiB**。最大的单项是仓储保存前 `ParseProjects` 全库回解析，中位 **440.7 ms**，占完整链路平均时间 **56.1%**，分配 **320.8 MiB**。这不是完整界面保存耗时；本测量不包含磁盘写入、刷新到磁盘、界面重新渲染和调度延迟。

数据为 10 项目 × 10 任务组 × 10 状态 × 20 任务，每个项目 2,000 任务，全库 20,000 任务。JSON 为 21,673,306 字符、25,209,826 字节。运行环境为 .NET 10.0.12、Windows build 26100、x64、28 个逻辑处理器、Workstation GC。

| 实际数据步骤 | 5 轮中位耗时 | 平均耗时占比 | 每轮平均分配 |
| --- | ---: | ---: | ---: |
| `ExportBackup` 全库撤销快照 | 86.7 ms | 13.4% | 91.3 MiB |
| `Clone` 全部 10 个项目 | 77.5 ms | 11.7% | 67.3 MiB |
| `SaveTask` 编辑单项目中的一个任务 | 18.9 ms | 2.6% | 9.7 MiB |
| `ExportInternal` 全库持久化文本 | 104.7 ms | 14.9% | 91.3 MiB |
| `ParseProjects` 全库回解析 | 440.7 ms | 56.1% | 320.8 MiB |
| 写入前 UTF-8 编码 | 10.7 ms | 1.3% | 24.0 MiB |
| 完整预 I/O 数据链 | **758.9 ms** | **100%** | **604.4 MiB** |

阶段中位数之和不必等于完整链路中位数。占比使用各阶段平均耗时除以完整链路平均耗时，避免混用中位数。原始逐轮结果、CPU 时间和 GC 次数保存在原审查工作区的 `winui/artifacts/scale-audit/serialization-benchmark.json`；该原始证据不随 GitHub 源码分发，普通 checkout 中不存在这份历史文件。

额外基线中，单独对全库执行 `EnsureValid` 中位 **7.3 ms**、分配 **14.9 MiB**；编辑器打开时克隆单个 2,000 任务项目中位 **8.3 ms**、分配 **6.7 MiB**。全库导出和回解析的阶段已包含对应领域校验，不能再把单独基线叠加到保存时间。

## 源码对应与解释

历史版本 `MainWindow.xaml.cs` 的 `CommitAsync` 先导出整个库的备份作为撤销记录，再克隆全部项目，然后执行修改和 `JsonProjectRepository.SaveAsync`。当时 `ProjectService.SaveTask` 又克隆目标项目，并在循环任务处理前后各校验一次。仓储接着导出全部项目，再使用完整导入解析器重新解析这些内部产生的 JSON，最后交给原子文件写入。

`PmSerializer.ParseProjects` 不只是 JSON 反序列化：它先建立 `JsonNode` 树，逐项目 `DeepClone`，内部格式转为 PM 包装时复制内容节点，结构检查后再复制回模型节点，最后反序列化并执行领域校验。`ValidateStructure` 还逐节点遍历整棵树，并为每个节点创建错误路径字符串。阶段测量证明整个回解析最重；这里对各个 DOM 子步骤的解释来自源码检查，未宣称已经分别测量它们的耗时占比。

`SaveAsync` 中的 `ConfigureAwait(false)` 也不等于把 CPU 工作移到后台。正常无竞争时信号量等待同步完成，后面的导出和回解析会继续在调用线程执行，直至遇到真正未完成的异步 I/O。当时从 UI 线程进入的保存路径因此可能在磁盘写入之前就阻塞约这一数据处理时间。当前界面延迟仍需要独立 GUI 证据确认，不能沿用旧调用路径推断。

当时撤销历史还有长期保留内存的问题：本夹具一份 `ExportBackup` 包含 21,675,475 个字符，单个 .NET 字符串的字符载荷为 **43,350,950 字节，约 41.3 MiB**，未包括对象头等开销。历史 `_undo` / `_redo` 为未设置容量上限的 `Stack<string>`，十次保存留下的十份类似快照仅字符载荷就约 413 MiB。当前实现已改为受步数、任务版本数和估算字节约束的项目历史；本基准每轮只保留一份旧式撤销快照，未模拟当前历史保留或长期资源趋势。

## 建议顺序

1. 先完成界面虚拟化和惰性菜单，让打开编辑器、切换视图等操作恢复响应；该基准支持将编辑器 DOM 构造与数据克隆分开处理。
2. 后续如优化保存，优先让隔离的数据事务在后台完成 CPU 处理，并在成功写入后回到 UI 线程更新模型、历史和界面。必须保留单次事务隔离、忙碌状态、失败不替换原模型和取消语义；仅增加 `ConfigureAwait(false)` 不会解决同步 CPU 阻塞。
3. 再优化内部格式的序列化/解析路径，减少不必要的 `JsonNode.DeepClone` 和临时模型构建。内部文件仍需完整的大小、结构、引用、依赖无环、扩展字段及往返校验，不能直接删除保存前回验来换取速度。外部 PM 文件、旧版本迁移、导入和同步边界仍需要同等保障。
4. 从事务模型上考虑仅克隆受影响项目、采用受控的项目级撤销记录，并给历史设置容量或内存预算。需要明确跨项目操作和完整恢复的语义，不能简单共享可变对象。
5. 双次领域校验在此规模下不是首要瓶颈，暂不以减少它为优化目标。任何保存路径改动完成后，再使用相同夹具和失败/恢复测试证明性能收益与数据保护均成立。

最初生成本报告的任务只新增测量模式与报告；后续修复已改变上述部分保存逻辑，所以这些建议需结合当前代码重新评估。

## 复现和边界

在 `winui` 目录执行：

```powershell
dotnet run --project tools/ScaleFixture/PureProject.ScaleFixture.csproj -c Release -- --profile 20k --benchmark --iterations 5
```

工具直接读取已标记夹具，以现有任务的标题编辑作为内存变更，按旧保存数据步骤的顺序调用当前 Core API。一轮预热后测量五轮，仅在完整轮次之间主动 GC，轮内自然 GC 计入耗时。计时器记录墙钟时间；CPU 时间来自 Windows 进程统计，较短阶段可能低于计时粒度；分配量使用当前线程累计分配计数。没有创建 `JsonProjectRepository` 实例、写夹具、启动 GUI 或调用 UI 自动化。

历史测量前后 `projects.json`、`settings.json` 和 `scale-fixture.json` 三个文件 SHA-256 均未改变。该过程没有模拟磁盘故障、长时间运行、后台竞争或多份撤销记录，不应据此宣称当前端到端保存已经优化。
